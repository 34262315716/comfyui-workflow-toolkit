## 两种 JSON 格式

ComfyUI 的同一个工作流有两套表示：

| | UI / store 格式 | API 格式 |
|---|---|---|
| 用途 | 画布存储（前端读写） | 提交给 `/prompt` 执行 |
| 结构 | `{nodes:[], links:[], groups:[], extra:{}, version}` | `{"<节点id>": {class_type, inputs}}` |
| 位置信息 | 有（`pos`/`size`） | 无 |
| 本工具 | **主战场** | 用 `export-api` / `import-api` 转换 |

`to_api()` 是把 UI 图转成执行图的那一步。**排版前后 `to_api()` 必须逐字节相同**——
这是全工具最重要的一条不变量，也是测试里最硬的一条断言。

## 三个真实世界的坑

### 1. `widgets_values` 有两种形态

控件值**不是**简单的数组：

- **位置数组**（老前端）：`[12345, 28, 6.5, "euler", "normal", 1.0]` —— 值靠**位置**对应控件
- **按名字典**（新前端）：`{"steps": 28, "cfg": 6.5, ...}` —— 实测本机库里 **146 处是这种**

还有更麻烦的：字典形态里混着 `videopreview` 这种**纯 UI 噪声键**（VHS 系节点的播放器状态），
不能当控件算。

**所以控件名从哪来？** 优先级：节点自带的名字 → `/object_info` 里该节点类型的控件顺序 →
当前 `inputs` 里那些"被转成端口"的控件。

这一步错了会怎样：改参数改到别的字段上去，而且**不报错**。所以 `set_widget`
必须按名字对位，且测试里专门有一条"改一个控件只许动那一个位置"。

### 2. 顶层 `links` 数组经常是陈旧的

实测某工作流的 `links` 里有一条记录 `origin_slot = 612`，而那个节点只有 2 个输出。
还有的情况是连线 id 与端口完全对不上。**ComfyUI 前端真正读的是节点上的 `link` 字段。**

所以解析时以**节点侧为权威**：
1. 从所有节点的 `outputs[].links` 建立 `link_id → (节点, 槽位)` 映射
2. 对每个节点的 `inputs[].link`，按这个映射重建连线
3. 顶层数组只用来补类型信息，对不上就修
4. 顶部有而节点侧没有引用的条目直接丢弃

自愈效果：全库 435 张、17173 条连线，解析后槽位 100% 合法。

### 3. `SetNode` / `GetNode` 不在 `/object_info` 里

它们是 **KJNodes 的前端 JS** 注册的节点，Python 侧根本没有。表现：

- 它们的 `outputs[].links` 里存的是**别的连线的 id**，不是自己的
- 校验时会报"节点类型不存在"——**这是误报**

判断依据：节点的 `properties.aux_id` 指向某个插件包 → 装过，只是没有后端实现。
`is_frontend_only()` 里维护了一份名单（`SetNode`/`GetNode`/`Reroute`/`PrimitiveNode`/rgthree 的开关等）。

顺带一提：`pos`/`size` 也有 3731 处是字典形态（`{"0":..,"1":..}`），
`_as_pair()` 负责容错。

## 代码结构

```
tools/cwf/
├── cli.py            命令行入口与全部子命令（约 2200 行）
├── lib/
│   ├── graph.py      图数据模型：Node / Slot / Link / Group / Graph
│   │                 加载（含上述三个坑的自愈）、序列化、编辑原语
│   ├── schema.py     /object_info 拉取与缓存、节点尺寸推算、Registry
│   ├── strata.py     排版引擎（分层图算法 + 几何自检）
│   ├── dsl.py        紧凑 DSL 解析器
│   ├── pack.py       模块切片 / 存 / 实例化
│   ├── catalog.py    节点库（本机装了什么节点、来自哪个包）
│   └── terms.py      中文别名（说"解码"→ VAEDecode）
└── tests/
    ├── harness.py    零依赖测试骨架
    ├── test_graph.py 数据模型（含"排版不改语义"硬断言）
    └── test_layout.py 排版质量（含测量工具自检）
```

**依赖：只用 Python 标准库。** 这是刻意的——工具要能在任何装有 ComfyUI 的机器上直接跑，
不需要先 pip install 一堆东西。

## 排版引擎

`strata.py` 里的 `Layouter`，流程（经典 Sugiyama 分层法 + 针对 ComfyUI 的特调）：

1. **规整化** —— 旁路/静音节点穿透；`SetNode/GetNode` 接回真实数据流
   （源头 → Set → Get → 下游，让跳线参与正常分层）；`Reroute` 收缩成点
2. **拆环** —— 深度优先找反馈边，反向后再分层
3. **分层** —— 最长路径分层 + 收紧（节点尽量往左靠）
4. **插虚节点** —— 长边在每个中间层放一个虚节点（**必须在排序之前**，
   否则逐层扫描的交叉数算的是节点序号而不是边的真实位置）
5. **层内排序** —— 中位数/重心启发式多轮扫描 + 逐对相邻交换精修
6. **坐标分配** —— 两趟中位数对齐取平均，长链自动拉直；横竖版式择优；
   层数过多时自动折行
7. **分区框** —— 按语义（加载/提示词/采样/解码/输出/放大/辅助）+ 连通性聚类；
   同区被拆散时按空间邻近合并；**大面积糊在一起的框直接合成一个**
8. **消重叠** —— 反复推挤直到收敛，任何两个节点（含注释）都不许重叠

### 关于"交叉数"的两个指标（重要）

工具里有两个不同的数字，**别搞混**：

| 指标 | 是什么 | 用途 |
|---|---|---|
| `report.crossings` | 逐层扫描：每层取一条竖直切割线，数所有跨线边的上下位置逆序对 | **优化目标**（排序阶段用它做爬山） |
| `count_geometric_crossings()` | 按正交路由算出折线，数真实相交的线段对 | **质量验证**（测试用） |

早期版本只数"相邻层之间的边"，导致横跨多层的长边完全不计分——
于是出现过「启发式报告 0 交叉、画布上 1704 处真实相交」这种自欺欺人的结果。
**教训：指标错了，优化就会朝着错误方向努力。**

### 路由

`route_edges()` 按 ComfyUI 的方式算走线：端口在节点**左右边缘**（不是中心），
走正交折线。相邻列的边在正中间折一次；跨多列的长边走虚节点给的位置。

**已知短板**：长边的水平段仍会从中间列的节点上经过（中位约 33% 的边）。
试过"逐列通道分配"的精细路由，结果交叉数翻倍、画布更乱，故回退。
这是纯外观问题，不影响接线正确性。

## 测试

零依赖，直接跑：

```bash
cd <仓库根>\tools\tests
<ComfyUI 的 python> -X utf8 test_graph.py     # 12 项
<ComfyUI 的 python> -X utf8 test_layout.py    # 20 项
```

**测试的核心价值不是"证明能跑"，而是"让指标无法自欺"**。它实际抓到过：

- 我声称的"全库 0 交叉"是假的（指标量错了对象）
- 一张图的节点重叠没收敛
- 315 节点的图排版要 **104 秒**（交换精修在大图上爆炸）
- `find_all` 解包错误（`type:` 选择器一用就崩）
- 几何检测函数本身有 bug（拿节点中心当端口位置）

### 硬指标 vs 软指标

**硬断言（必须 0）**：
- 任何两个节点都不重叠（全库 435 张）
- 分区框都套住了自己的成员
- 排版后 `to_api()` 逐字节不变
- 排版后接线（源槽→目标槽）与控件值逐项不变
- 改一个控件只许动那一个位置
- 往返序列化幂等

**软指标（卡阈值防回归）**：
- 连线穿节点率：中位 33% / p90 67%（阈值 45% / 80%）
- 交叉密度：中位 1.0/边（阈值 3.0）
- 分区框压边比例：9.9%（阈值 18%）
- 长宽比、每节点占位、排版耗时

### 测量工具自检

`test_layout.py` 开头四条"已知答案对照"——先证明尺子准，再用尺子量：

1. 两条平行链 → 0 交叉、0 穿节点
2. 一条线穿过中间节点 → 恰好检出 1 处
3. 一条干净的线 → 0 / 0
4. 端口锚点在节点**边缘**而非中心

**没有这四条，后面的数字全是假的。**
